# Contributing

Thanks for your interest in cssert.

Issues and pull requests are welcome at <https://github.com/tokibito/cssert>.
Everything that lands in the repository — code, comments, TSDoc, commit
messages, pull request descriptions, documentation and CLI output — is
written in English.

## Getting set up

Node.js 20 or newer and pnpm. The exact pnpm version is pinned in
`package.json` (`packageManager`), so `corepack enable` gives you the right
one without a global install.

```bash
git clone https://github.com/tokibito/cssert.git
cd cssert
pnpm install
```

pnpm 10+ refuses to run dependency build scripts unless they are allowed;
the only one we need (`esbuild`) is listed in `pnpm-workspace.yaml`. If
`pnpm install` complains about ignored build scripts, that file is where to
look.

## Running the tests

```bash
pnpm test               # vitest, once
pnpm vitest             # watch mode
pnpm test:coverage      # with the coverage thresholds CI enforces
```

Tests live in `test/` and mirror `src/` (`test/core/`, `test/extract/`,
`test/cli/`, …). Coverage thresholds are enforced in `vitest.config.ts`:
**95 % for `src/core/`** and 80 % elsewhere. A change that drops below them
fails CI.

CLI tests run the commands in-process against a temporary directory through
`test/cli/helpers.ts`; nothing is spawned, nothing touches the repository.
One test additionally executes the built binary and is skipped when `dist/`
does not exist, so `pnpm build` before `pnpm test` exercises it.

### Fixtures are real build output

`test/fixtures/*.css` are generated by Tailwind v3, Tailwind v4 (two
versions: flat and nested output) and UnoCSS from the sources under
`test/fixtures/src/`. Do not edit the generated files by hand; regenerate them
with

```bash
scripts/build-fixtures.sh   # needs network access, uses npx
```

and commit the result together with the source change. Hand-written CSS is
fine for focused unit tests, but anything that claims to cover "what Tailwind
emits" has to be checked against these files. Only our own sources go in; no
third-party project code.

## Linting, formatting and types

```bash
pnpm lint         # biome check
pnpm lint:fix     # biome check --write
pnpm typecheck    # tsc --noEmit
```

Biome handles both linting and formatting; there is no ESLint or Prettier.
CI runs `pnpm lint` and `pnpm typecheck` and fails on unformatted code rather
than fixing it. The `strict`, `noUncheckedIndexedAccess` and
`exactOptionalPropertyTypes` compiler options are on; an optional property
has to be omitted, not set to `undefined`.

## Making a change

A few things are easy to forget:

- **The design brief comes first.** `src/core/` is pure: no I/O, no thrown
  exceptions, failures are returned as `warnings`. Only `src/cli/` reads
  files. The HTML-derived audit is the primary feature; explicit assertions
  are secondary. cssert never rewrites CSS and never guesses a cascade
  winner. A change that needs to bend one of these points needs an issue
  first.

- **Decisions go in `docs/decisions.md`.** Whenever you settle something the
  specification does not cover, or deviate from it, add a numbered entry with
  the reasoning. The file is the record of *why*; the code only shows *what*.

- **A changeset.** Run `pnpm changeset`, pick `patch` or `minor`, and describe
  what a user of the package will notice. Commit the generated file under
  `.changeset/`. Leave `version` in `package.json` and `CHANGELOG.md` alone;
  releases are cut from the changesets (see
  [docs/releasing.md](docs/releasing.md)). Pure refactors, test-only and
  docs-only changes need no changeset.

- **Class-name normalisation.** Anything that touches `src/core/normalize.ts`
  is the highest-risk change in the repository: a mistake there makes every
  audit report false positives. Add a case to `test/core/normalize.test.ts`
  for each new shape of escape you handle, and check the fixtures still pass.

- **The README and recipes.** New flags, config keys and report formats are
  documented in `README.md`. The recipes under `docs/recipes/` show commands
  end to end; a changed command line usually shows up in all three.

- **CLI output is part of the contract.** The `json`, `github` and `sarif`
  formats are consumed by machines. Add fields rather than renaming them, and
  bump the `version` field of the JSON report if you must break it. Exit
  codes (0 clean, 1 violations, 2 usage, 3 internal) do not change.

### Backwards compatibility

Projects depend on the config file keys, the CLI flags, the report formats,
the baseline and budget file layouts, and the exported functions and types.
While we are on `0.x` breaking changes are possible, but they still need a
`minor` changeset that says so plainly, a note in the README, and where
feasible a release that keeps the old form working with a warning first.

The tests are the safety net. When a refactor leaves the existing tests
passing unmodified, that is the evidence that behaviour did not change.

## Trying it against a real project

```bash
pnpm build
node dist/cli/index.js check --css path/to/built.css --html "path/to/**/*.html"
```

or `pnpm link --global` and use `cssert` directly. Real Tailwind output from
your own project is the best test there is; if it surfaces a false positive,
reduce it to a fixture and open an issue with the CSS snippet and the class.

## Pull requests

- Branch off `main`.
- **One purpose per pull request.** See below.
- Say what the change is for. A description that explains the problem is
  worth more than one that restates the diff.
- Keep the tests, the linters and the type check green. CI runs the suite on
  Node 20, 22 and 24, and the coverage job on Node 22.
- Add tests for a behaviour change. A bug fix wants the test that fails
  without it. A parser fix wants the smallest CSS that reproduces it.
- Commit messages follow Conventional Commits (`feat(core): …`, `fix(cli): …`,
  `docs: …`, `ci: …`).

### Split by purpose

A pull request should answer one question, so that a reviewer can hold that
question in their head while reading all of it. Several purposes in one
branch means none of them gets read properly, and the risky part hides among
the safe parts.

Split it when a branch contains any of these:

- **A refactor and the feature it makes possible.** Send the refactor first,
  where the existing tests passing unmodified is the whole argument, and build
  on it afterwards.
- **A fix for something you noticed on the way.** Worth having, and worth
  having on its own, where it can be reviewed and reverted by itself.
- **Mechanical churn beside a real change.** Reformatting, renaming,
  dependency bumps and regenerated fixtures drown the few lines that matter.
- **Steps that make sense in sequence.** A new field in the parser model, the
  query that exposes it, the CLI flag and the documentation can each be a
  pull request, each mergeable on its own.

This holds however the change was produced, including with the help of an AI
tool. A branch that grew in one sitting still has to arrive as the sequence
of changes a reviewer can follow; splitting it afterwards is part of the
work, not an optional tidy-up.

A change that genuinely is one purpose can still be large, and that is fine.
The test is whether the description needs the word "and".
